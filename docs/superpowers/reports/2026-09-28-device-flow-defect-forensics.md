# Device-flow browser confirm loop — forensics (2026-09-28)

**Symptom** (reproducible, integration day): fresh user_code → GET /oidc/device?user_code auto-submits → confirm page renders → clicking Continue POSTs `confirm=yes` → **provider returns 200 re-rendering the confirm page; no 302 to login; token polling never completes**. `DeviceCode.inFlight=true` lands in DB (poisoning retries of the same code with AlreadyUsedError 200s).

**Bisect experiment** (config `features.devInteractions.enabled=true`, everything else unchanged): the confirm POST DOES 302 — to `/oidc/interaction/:uid`, where **our own bearer decorator answers `AUTH_001` JSON** (the dev route sits under the /oidc mount and our auth surface intercepts it). So the interactions middleware chain runs and interaction start-up works; the failure domain is precisely **the redirect target produced by our `interactions.url` (oidc/provider.ts:163)** — under production config, its return value never takes the browser anywhere (observed as the 200 re-render).

**Prime suspects (fix batch must check in order):**
1. Device-flow interaction prompt name: our url() branches only `prompt.name === 'login'`. If the device interaction's prompt is named otherwise (e.g. 'device'), we fall to the ELSE branch returning a **relative** `/consent?...&resume=%2Foidc%2Fdevice...` — check what the provider/browser actually do with it (404 swallowed into re-render? issuer-relative redirect?). Log prompt.name at runtime — 10-minute answer.
2. `interaction.returnTo` for device flows may not be a parseable absolute URL → our `new URL()` catch → fallback `/oidc/auth/:uid` — wrong resume for device (auth vs device resume routes).
3. Cross-origin cookie reality: session/interaction cookies are site=127.0.0.1:5101; the SPA on localhost:5173 is cross-site for SameSite=Lax... the e2e lane runs vite+API same host (localhost) so it never sees this; our repro used 127.0.0.1 for API + localhost for UI — **part of the loop may be a hostname split of the harness, not product**. Fix the harness (same host both sides) FIRST, then re-run before touching code.
4. If prompt.name IS 'login': the absolute `${frontendOrigin}/login?redirect=...` should have navigated to 5173 — it did not. Which means url() wasn't consulted at all → the 200 came from an earlier rejection (xsrf/state?) — instrument: log inside interactions.url.

**Repro recipe** (scratch env): create db ab_intday → db:push → tsx server (DATABASE_URL/REDIS_URL/FRONTEND_ORIGIN=http://localhost:5173/JWT_SECRET/DEBUG=oidc-provider:*) → setup/admin → login → POST /clients (grantTypes auth_code + device_code) → POST /oidc/device/auth → playwright chromium goto verification_uri_complete, click Continue, watch NAV lines + SELECT payload->>'inFlight' FROM oidc_adapter_state WHERE kind='DeviceCode'.

**Fix batch scope proposal (P1 device-flow 收口):** (a) diagnose + fix the redirect (suspects 1-2 above); (b) branded server-side device pages replacing library defaults (userCodeInputSource/userCodeConfirmSource/successSource/renderFailed overrides — same-origin, no cross-site cookie dance, i18n, dark-safe) — this ALSO kills suspect 3 permanently; (c) vitest supertest battery: full device round WITHOUT browser (input POST → login via /auth API with cookie jar → resume → token); (d) e2e stays mock-API (can't cover provider), the supertest battery IS the regression net; (e) Q3D back-channel live-RP check rides the same battery (our own RP as the counterparty).
