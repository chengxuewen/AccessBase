## 1. UI FUNCTION SURFACE (24 pages, 28 routes — the admin + self-service map)

### 1.1 Coverage verdict: every page has SOME e2e, but coverage is named-spec-based, not capability-based

24/24 pages route to an e2e spec (via name mapping: ApiKeys→api-keys,
Audit→audit-viewer, Consent→oidc-consent, Login→auth-session+oauth-login+login
specs cluster, Tenants→tenants-crud, etc. — zero orphan pages). The i18n pair
is drift-free (695 keys, en-only 0 / zh-only 0). Permission gates census
shows every gated page carries its codes (webhooks:write, tenants:delete,
options:_, groups:_, clients:write, audit:read, apikeys:write...).

**Real gaps are capability-level, not page-level:**

- **UI-1. Dark mode is present but untested at page level** — theme.spec exists
  but the 13 post-§14 pages (Groups/Webhooks/Events/Tenants/Clients/ApiKeys +
  self-service six) have no dark-mode sweep; the G8 device-flow pages carry
  their own dark CSS (unit-covered) — fine — but the admin pages' dark mode
  relies on LocaleGate algorithm only.
- **UI-2. No page-level a11y sweep** — §14.16 a11y bar is the only documented
  standard; pages were built with aria labels opportunistically (Q1 wave),
  no axe/coreWebVitals audit exists.
- **UI-3. Responsive/mobile** — §37.6 mobile is design-doc-only; the admin
  pages are desktop-shaped (ProTable min-widths, fixed cards); no mobile
  viewport sweep exists.
- **UI-4. The G7 monolith quartet (Login 678 / Settings 614 / Webhooks 535 /
  Groups 527) still open from v1** — churn data now backs it: Login.tsx 20
  touches/60d, Settings.tsx 11/60d — every new slice multiplies re-reading
  cost.
- **UI-5. consent.tsx and EnrollMfa.tsx have the thinnest e2e** (consent via
  oidc-consent 8 tests, enroll-mfa via q1-self-service) — the thinnest are
  the provider-facing pages (consent renders provider-driven data; no test
  asserts the branded shell on consent (G8 covered device pages, NOT consent).

### 1.2 Branding slice reach is inconsistent

Branding (logo/primary) applies to: Login ✅, Consent ✅, device-flow pages ✅
(G8), AdminLayout ✅. NOT reached: Setup wizard, self-service pages
(Forgot/Reset/Register/VerifyEmail/MagicLogin), Dashboard. **Minor gap** —
operator-configured logo not appearing on forgot-password is a visible
inconsistency. Cheap fix: extend useBranding to the self-service cluster.

## 2. TEST BLIND-SPOT MAP

### 2.1 Route-level vitest coverage — the "0 referenced" files are false alarms, with two exceptions

`routes/audit.ts`, `routes/clients.ts`, `routes/setup.ts` show 0 direct
references but are covered indirectly (audit-viewer e2e + audit-logs.test,
clients-routes.test, setup-status.test / setup.test / route-guard.test all
exercise them — the grep missed import-path forms). **The two genuine
blind spots:**

- **T-1. `routes/auth.ts` is now a 121-line façade re-exporting the 8-module
  split** — its tests reference `routes/auth.js` in 3 files, but the
  **split modules' direct coverage is by aggregation** (auth-sessions,
  auth-refresh, auth-events, route-guard, auth-rbac, PIT-086 gates in e2e).
  The façade itself has no import-graph test — the W1-6 process-defenses
  source-lock covers it. Acceptable; noted.
- **T-2. `oauth-backchannel-logout.ts` (the Q3D receiver) has ONE test file
  (integration, real-PG) + the U battery lives on the util** — but the route
  layer's scoped parser/error-handler/rate-limit/audit-exclusion quadruple
  has NO unit lane: the integration file covers parser+handler through the
  full app; a parser-only failure mode (Content-Type variants) would only
  surface at live-fire. **Recommended: 2 unit cases (content-type variants)
  in bclo route tests — 30 minutes.**
