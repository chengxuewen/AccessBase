# Batch I — SMS OTP Login + Provider Abstraction (Design)

**Status**: Proposed 2026-09-16
**Origin**: Gap-analysis P2 final item (SMS OTP). Librarian-verified: provider landscape + NIST 800-63-4 position + codebase mapping (2026-09-16).
**Level**: Bounded-medium — provider abstraction + two endpoints + TOTP non-downgrade chain. All consuming patterns are established (FlowTokenService/LockoutService/Mailer.fromConfig precedent).

## 0. Architecture rulings

- **Provider abstraction**: `SmsProvider` interface `{ send(params: {to: string; code: string}): Promise<void> }` in identity package. Two adapters v1: **aliyun** (Dysmsapi SendSms, template-based, SDK `@alicloud/dysmsapi20170525` + `@alicloud/openapi-client`) and **twilio** (raw SMS via `messages.create`). No Verify API coupling (app owns the code). Tencent deferred (weak ESM; backlog).
- **App owns the code**: 6-digit numeric generated by our code (`crypto.randomInt(100000, 1000000)`), stored in FlowTokenService payload `{ userId, phone, code }`, TTL 300s. Provider adapter maps `{to, code}` → provider-specific template/message.
- **TOTP non-downgrade (critical)**: if `user.totpEnabled` → SMS consume must NOT mint a session directly; it issues a `mfa_verify` flow token (same as magic-link consume). SMS OTP never bypasses stronger MFA.
- **NIST positioning**: SMS OTP is a restricted authenticator (NIST 800-63-4 §3.1.3.3); docs must note TOTP/passkeys as recommended alternatives. Not blocking for v1.
- **No new permission codes**: /sms-otp/* are public auth endpoints (same family as login/ldap/magic) — seed stays 21.

## 1. Scope

### I1: SmsProvider (identity package)

- `SmsProvider` interface: `send(params: {to: string; code: string}): Promise<void>` — throws on provider error; caller handles fire-and-forget.
- `SmsProvider.fromConfig(cfg: SmsConfig): SmsProvider | null` — static factory; returns null when required config absent (mirror Mailer.fromConfig). Null → caller logs warn + still 202.
- **SmsConfig** (options table + env fallback, `get()` pattern):
  - `sms_provider` / `SMS_PROVIDER` ('aliyun' | 'twilio'; empty → disabled)
  - `sms_sign_name` / `SMS_SIGN_NAME` (aliyun/tencent: approved signature)
  - `sms_template_code` / `SMS_TEMPLATE_CODE` (aliyun: TemplateCode e.g. SMS_123456)
  - Per-provider credentials via env only (secrets not in options table, same as SMTP pass):
    - aliyun: `ALIBABA_CLOUD_ACCESS_KEY_ID` + `ALIBABA_CLOUD_ACCESS_KEY_SECRET`
    - twilio: `TWILIO_ACCOUNT_SID` + `TWILIO_AUTH_TOKEN` + `TWILIO_FROM_NUMBER`
- **Aliyun adapter**: `@alicloud/dysmsapi20170525` + `@alicloud/openapi-client` — `SendSmsRequest({phoneNumbers, signName, templateCode, templateParam: JSON.stringify({code})})`. Lazy client construction (mirror SamlProvider lazy pattern). Config validity: enabled + signName + templateCode + credentials all non-empty.
- **Twilio adapter**: `twilio` npm — `client.messages.create({to, from, body: \`您的验证码是 ${code}，5分钟内有效\`})`. Config validity: enabled + accountSid + authToken + fromNumber.
- **Exports**: `SmsProvider`, `SmsConfig` from identity index.ts.
- **Error handling**: adapter throws on provider API error; caller (route) catches + logs + still 202.

### I2: SMS OTP endpoints (routes/auth.ts, after magic-link block)

- `POST /api/v1/auth/sms-otp/request` `{phone: string}`:
  - Rate limit: 5/15min per IP (mirror magic/request).
  - Body schema: `{phone: {type:'string', pattern: E.164 regex}}` → 400 on invalid.
  - **Always 202** `{success:true, data:{message:'If an account exists, a verification code has been sent.'}}` (enumeration resistance).
  - Internal: `userManager.findByPhone(phone)` — **needs new column** (see Non-goals for v1 alternative). **v1 ruling**: lookup by `phone` requires a `users.phone` column. **Decision**: add `users.phone` column (nullable, non-unique at v1) in migration 0004 — same drizzle-kit generate as any batch. Without a registered phone → still 202, no send.
  - User found && active → generate code (`crypto.randomInt(100000, 1000000).toString()`), `flowTokens.issue('sms_otp', {userId: user.id, phone, code}, 300)`, SmsProvider.send fire-and-forget. SmsProvider null → log warn + still 202.
- `POST /api/v1/auth/sms-otp/verify` `{token: string, code: string}`:
  - Rate limit: 10/15min per IP.
  - `flowTokens.consume(token, 'sms_otp')` → null → 401 `AUTH_SMS_001` generic.
  - **Lockout on phone**: `lockout.recordFailure(phone)` on wrong code; `lockout.isLocked(phone)` → 403 AUTH_004 family; `lockout.clear(phone)` on success. (Reuse existing LockoutService — identifier = phone string.)
  - code mismatch → 401 AUTH_SMS_001 (token already burned by consume — user must re-request).
  - user lookup (findById) → suspended → 403 AUTH_004.
  - **TOTP non-downgrade**: `user.totpEnabled` → `flowTokens.issue('mfa_verify', {userId}, 300)` → `{mfaRequired:true, flowToken}` (same shape as magic consume).
  - else → `issueTokenPair(request, user)` → token pair (same shape as login).
  - 200 response schema: union of mfaRequired/flowToken + accessToken/refreshToken/expiresIn/user (mirror magic consume).
- Error codes: `AUTH_SMS_001` (401 invalid/expired OTP) — one code, generic message.
- **No new permission codes** (public auth family — seed stays 21).

### I3: TOTP non-downgrade chain

- Already covered in I2 verify: `totpEnabled → mfa_verify` (not a direct session). **This is the critical constraint** — without it, SMS becomes a TOTP bypass. The chain mirrors magic-link consume exactly.
- PIT-052 matrix: SMS issuance adds row `sms-otp-verify` → mfa_verify {userId} 300s (six→seven issuance points, all same shape).

## 2. Non-goals (backlog)

- users.phone column + phone binding management (settings UI) — v1 ruling: add nullable column in migration 0004, but phone binding/management API deferred. For now, phone is set via DB only (or SCIM metadata extension later).
- SMS as MFA recovery/bypass (explicitly forbidden — TOTP non-downgrade).
- SIM-swap detection, multi-language SMS templates, SMS delivery reports, phone number change audit trail.
- Tencent Cloud adapter (weak ESM; add when market demands).
- Resend cooldown 60s (FlowTokenService TTL 300s already limits to 1 code per 5min per token; the rate limit 5/15min caps abuse).

## 3. Tests

- Unit (identity): SmsProvider.fromConfig null-when-unconfigured; aliyun adapter sends correct template params; twilio adapter sends correct body; adapter throws on API error.
- Route (apps/server): request → 202 identical body (enum-safe); invalid phone → 400; unregistered phone → 202 (no send); verify happy → token pair; verify totp user → mfaRequired+flowToken (NOT session); verify wrong code → 401 + lockout.recordFailure; verify expired token → 401; verify suspended user → 403 AUTH_004; verify locked phone → 403.
- PIT-056: probe assertions on manager calls (findByPhone/issue/consume args).

## 4. Constraints

- New deps: `@alicloud/dysmsapi20170525` + `@alicloud/openapi-client` + `twilio` (identity package).
- Migration 0004: users.phone varchar(20) nullable (single drizzle-kit generate).
- PIT standing: 048/051/053/054/055/056/057.
- PIT-052 matrix update: sms-otp-verify row → mfa_verify {userId} 300s.
