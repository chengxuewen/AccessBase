# think-before-act — 先调研→列方案→用户审批→(团队审核)→执行

> 不蛮干。

## 触发条件

任何**非平凡**操作：调试、测试、实现、重构、修复、配置变更、升级。

---

## 决策门（每次操作前自问）

1. **"官方推荐怎么做？"** → 不知道就去查，别猜。
2. **"项目之前遇到过吗？"** → 查项目知识库（`.agents/memorys/` / `git log`）。
3. **"社区有人解决过吗？"** → 搜 issue / 论坛 / StackOverflow（用错误信息原文搜）。
4. **"用户同意这个方案吗？"** → 列方案等审批，别直接改。
5. **"上一次尝试为什么失败？"** → 说不清就别试下一个。

---

## 分级

| 档位     | 判据                                              | 流程              |
| -------- | ------------------------------------------------- | ----------------- |
| **平凡** | 不改接口/构建/依赖，可逆，单文件，无副作用        | 直接做 + 一行说明 |
| **标准** | 改接口/构建/依赖/多文件/不可逆/框架级问题         | Phase 1→2→3       |
| **紧急** | 用户明确声明"紧急/先修后报"（生产宕机、数据丢失） | 先做 + 事后补报告 |

---

## Phase 1: 调研（标准档禁止跳过）

### 5 层知识源（按优先级）

1. **项目历史**: `.agents/memorys/` / `git log`
2. **语言/工具链原生文档**: `tsc --help` / `pixi run --help`
3. **框架/工具官方文档**: 找推荐做法，不是随便搜
4. **社区经验**: GitHub issues / StackOverflow / 论坛（搜错误信息原文）
5. **类似项目**: 同技术栈开源实现怎么做的

### 测试场景额外清单

- [ ] 项目测试约定（框架? AAA? 命名? 覆盖率?）
- [ ] 规格/契约文档 → 提取测试场景
- [ ] 已有测试模式（同模块怎么测的? fixture?）

### 输出

调研摘要：找到了什么、官方推荐什么、项目约定是什么。

---

## Phase 2: 列方案（标准档，禁止自动执行）

### 格式

```
方案 A: [描述] — 优势 / 劣势 / 影响范围
方案 B: [描述] — 优势 / 劣势 / 影响范围
推荐: [X]，理由: [...]
```

### 代码变更必须列出

- 哪些文件会被修改
- 修改内容摘要（不是完整 diff）
- 潜在风险
- 回滚方式

### 审批

列方案 → 等待用户确认。

- 沉默 / 超时 / "继续" ≠ 批准
- 必须用户显式肯定响应
- 部分批准（"做 A 不做 B"）→ 只执行被批准的部分

### 复杂变更：团队审核

对于复杂变更（改构建/改架构/框架级问题/影响 >5 文件），
用户审批后、执行前，增加团队审核环节：

```
1. team_create — 创建审核团队（3 视角）
2. 收集审核反馈 → 修订计划
3. 用户确认修订 → 进入 Phase 3
```

审核发现的 CRITICAL 项必须修复。LOW 项可记录为技术债。

---

## Phase 3: 执行（用户已审批）

- 按用户选择的方案执行
- 每步验证（不积累未验证变更）
- 失败时: 回滚 + 报告，**不自动尝试方案 B**（回到 Phase 1 补充调研）

---

## 核心铁律

1. **无新信息 = 无新尝试。** 失败后换参数再试，没有新诊断信息就是在蛮干。
2. **测对层级。** 单元(逻辑) / 集成(边界) / E2E(用户流) / 验收(业务) — 不同层级捕获不同故障。
3. **平凡代码无需测试。** 一行、无分支、无副作用 → YAGNI 适用于测试。

---

## 测试层级速查

| 层级       | 捕获什么     | 工具                                 |
| ---------- | ------------ | ------------------------------------ |
| 单元       | 逻辑错误     | `pixi run npx vitest run`            |
| 集成       | 接口不匹配   | `pixi run npx vitest run` (AAA 模式) |
| E2E        | 用户路径断裂 | `pixi run npx playwright test`       |
| TypeScript | 类型错误     | `pixi run npx tsc --noEmit`          |

---

## 禁止清单（做 X 前先验证 Y）

| 想做                  | 先验证                             |
| --------------------- | ---------------------------------- |
| 改配置/改构建         | 查了官方推荐配置方式               |
| 失败后再试一次        | 有新的诊断信息（不是换参数碰运气） |
| 编辑生成文件/编译产物 | 确认修改不会在下次构建时被覆盖     |
| 删除不理解的东西      | 确认它不是被其他模块依赖的         |
| 直接编辑文件          | 用户已审批方案                     |
| 在项目环境改依赖/pnpm | 本地验证通过后再改                 |

| Karpathy 原则             | 本技能对应                   |
| ------------------------- | ---------------------------- |
| **Think Before Coding**   | Phase 1: 调研 + 5 层知识源   |
| **Simplicity First**      | 核心铁律 + 分级（平凡/标准） |
| **Surgical Changes**      | Phase 2: 列方案 + 禁止清单   |
| **Goal-Driven Execution** | Phase 3: 执行 + 决策门       |
